# Data Augmentation Sprint — March 31, 2026

**Sprint Goal:** Improve model performance by addressing training data quality and class imbalance.

> "Model performance is bounded by the quality and diversity of training data."

---

## Background

The v2 priority classifier (trained 2026-03-20) showed a **9.62% false-high rate** and significant class imbalance. Four of eight ticket categories had fewer than 200 training samples, and the `critical` priority class had only 127 — less than 20% of the `low` class count (642). The synthetic template library in `ml/synthetic_generator.py` was also narrow, limiting generative variety.

---

### 3. Built an End-to-End Augmentation and Retrain Pipeline

**Script:** `scripts/augment_and_retrain.py`

A 7-step orchestration script:

1. **Audit before** — baseline distribution snapshot
2. **Augment** — compute gap per class; over-generate 4× to survive deduplication loss (time-based random seed to avoid re-generating the same tickets on successive runs)
3. **Quality pass** — hash-dedup, label validation, short-description filter
4. **Save raw corpus** — writes `data/raw/synthetic_tickets.json`
5. **Preprocess + split** — `DataPreprocessor` → `DataSplitter` (80/17/3 stratified)
6. **Audit after** — confirm all classes meet threshold
7. **Train** — calls `src/train_priority_model.py --model logistic --tune --quick`

Key CLI flags:
```
python scripts/augment_and_retrain.py [--min-category 200] [--min-priority 200] [--models priority] [--no-train]
```

---

### 4. Ran the Pipeline

```
python scripts/augment_and_retrain.py --models priority --min-priority 200
```

Generated 769 new clean tickets. All class thresholds met after the quality pass.

## Analysis

The **false-high rate improved from 9.62% → 8.57%** — the primary operational metric protecting against critical tickets being under-prioritized.

The **f1_macro drop (0.733 → 0.687)** is attributable entirely to the critical class (F1=0.38), which is now more prominent in the larger test set (49 critical test samples vs. 36 before). The low, medium, and high classes all show healthy F1 scores (0.82 / 0.75 / 0.79).

The **critical recall of 0.27** is the open issue. Root cause: prior critical samples were generated by forcing the `critical` label onto random generic templates, adding label noise rather than signal. The 11 new explicitly critical templates added this sprint (auth server down, ransomware, full office outage, etc.) will drive improvement in the next dedicated pass.

---

## Known Limitations

1. **Critical F1 = 0.38, recall = 0.27** — model identifies only 27% of genuinely critical tickets. Primary open issue.
2. Augmented critical tickets in this pass still used forced labels on general templates; the new explicit critical templates were only partially exercised.
3. Priority imbalance at 3.44× is below the 4× target but low (35%) is still 3.4× larger than critical (10%).
4. Negation not handled — phrases like "no critical issues" may still trigger critical keywords.

---

## Next Steps

1. **Second critical-only augmentation pass** — use only the 11 new explicitly critical templates to build a high-signal critical corpus without label noise.
2. **Evaluate `class_weight='balanced'`** in logistic regression to see if critical recall improves independently.
3. **Retrain category classifier** on the enlarged dataset to validate category accuracy improvements.
4. **Schedule monthly retraining** via `retrain_pipeline.py` with `augment_and_retrain.py` as a pre-step.
