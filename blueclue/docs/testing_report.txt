TEST CASE 5 - EDGE CASE
Name:    Wireless Mouse Category Ambiguity
Type:    Edge Case
================================================================================

DESCRIPTION:
  The message "Mouse keeps disconnecting from wireless receiver" contains
  hardware keywords ("mouse", "receiver") AND network keywords ("wireless",
  "disconnect", "disconnecting"). This tests how the classifier resolves
  a cross-category ambiguity.

INPUT:
  "Mouse keeps disconnecting from wireless receiver"

EXPECTED RESULTS:
  category   = "hardware"  (mouse, receiver are hardware devices)
  subcategory = "peripheral" or "wireless"
  confidence >= 0.60

ACTUAL RESULTS:
  category   = "network"   (confidence: 1.00)
  subcategory = "connectivity"
  keywords matched: ["wireless", "disconnect", "disconnecting",
                     "keeps disconnecting"]

OUTCOME: FAIL
ANALYSIS:
  The keywords "wireless", "disconnect", and "disconnecting" have high weights
  (3.0-4.0) in the network/connectivity category. The hardware keyword
  "mouse" has a lower weight (2.0). The network keywords collectively score
  higher and win. Confidence of 1.00 shows the scorer is very certain about
  the wrong answer.

  This case is documented in test_results.md as a known failure. It represents
  an inherent ambiguity in the keyword overlap between hardware peripherals
  and network connectivity. The fix would require a compound rule: if
  "wireless" + "mouse" co-occur, score hardware/peripheral over
  network/connectivity.

IMPACT:   Low - this is a rare ticket type. The technician can manually
          recategorize after submission with one click.
TRACKED:  Yes - this exact case is documented in the failed tests section
          of test_results.md as a known limitation.

TEST CASE 12 - ERROR HANDLING
Name:    Stale Chat Handoff Claim Auto-Release
Type:    Error-Handling
================================================================================

DESCRIPTION:
  When a technician claims a chat handoff but disconnects without resolving
  it, the conversation becomes permanently locked to that technician.
  No other tech can claim it. The system must automatically detect and
  release stale claims so the customer is not left waiting indefinitely.

SETUP:
  chat_conversations row with:
    handoff_requested = true
    handoff_claimed_by = [technician_id]
    handoff_claimed_at = 2 hours ago
    ended_at = null

INPUT:
  node-cron scheduled job fires (or manual trigger of the stale handoff
  release function)

EXPECTED RESULTS:
  - handoff_claimed_by reset to NULL
  - handoff_claimed_at reset to NULL
  - Conversation becomes available for any technician to claim
  - Technician workload dashboard shows conversation as "waiting" again
  - Socket.IO event broadcast: 'handoff_available' emitted to technician rooms

ACTUAL RESULTS:
  - handoff_claimed_by = NULL after cron job                     PASS
  - handoff_claimed_at = NULL                                    PASS
  - Conversation visible again in technician handoff queue        PASS
  - A second technician was able to claim it immediately          PASS
  - Socket.IO 'handoff_available' event received by clients
    (verified in browser DevTools Network tab)                   PASS

OUTCOME: PASS
NOTES:   This bug was discovered when conversation id=10 became permanently
         stuck in production. Migration 037 (037_reset_stale_handoff_claims.sql)
         was applied directly to the Railway database to fix the immediate
         stuck record. The cron-based auto-release was then implemented as
         the permanent preventive solution. The direct SQL fix is documented
         in the terminal history:

           UPDATE chat_conversations
           SET handoff_claimed_by = NULL,
               handoff_claimed_at = NULL,
               handoff_resolved_at = NULL,
               ended_at = NULL
           WHERE id = 10;

KNOWN LIMITATIONS & CLASSIFICATION EDGE CASES
================================================================================

1. WIRELESS PERIPHERAL AMBIGUITY [Case 5 - FAIL]
   Input:   "Mouse keeps disconnecting from wireless receiver"
   Got:     category="network" (confidence: 1.00)
   Expected: category="hardware"
   Cause:   "wireless", "disconnect", "disconnecting" carry weights 3.0-4.0 in
            the network/connectivity category; "mouse" only weighs 2.0 in
            hardware. Network keywords win collectively.
   Impact:  LOW - rare ticket type; technician can recategorize in one click.
   Fix:     Requires a compound rule: if "wireless" + peripheral device name
            co-occur, score hardware/peripheral over network/connectivity.
   Status:  OPEN - tracked in test_results.md.

2. PRIORITY ACCURACY AT 66.7%
   The AI tends toward "medium" for tickets that should be "high" or "low".
   Root cause: synthetic training data underrepresents extreme priorities.
   Impact:  MEDIUM - technicians should review auto-assigned priorities for
            tickets near threshold language.
   Status:  OPEN - identified as a training data gap.

3. O(n) EMBEDDING RETRIEVAL (RAG PIPELINE)
   KB article retrieval performs a full cosine-similarity scan over all
   article embeddings. Acceptable at current article count (<100) but will
   degrade at scale (1,000+ articles) without pgvector indexing.
   Impact:  LOW for current deployment; MEDIUM for future scale.
   Status:  OPEN - pgvector migration is a backlog item.

4. STALE CHAT HANDOFF IN PRODUCTION [RESOLVED]
   chat_conversations row id=10 became permanently locked when a technician
   disconnected mid-claim. Hotfix: migration 037_reset_stale_handoff_claims.sql
   applied directly to Railway DB. Permanent fix: node-cron auto-release job
   (tested in Case 12). Status: RESOLVED.

5. SHAP FLAT ARRAY COMPATIBILITY [RESOLVED - PR #260]
   SHAP explanation values returned as nested arrays in some SHAP versions,
   causing abs() / sorted() to fail on non-scalar elements.
   Fix (merged 2026-04-03, branch ml-error-fix):
     - vals = np.asarray(vals).flatten()   ensures 1-D float array
     - key=lambda x: float(abs(x[1]))      forces scalar comparison
     - Enhanced fallback: if model has no feature_importances_, fall back
       to _keyword_fallback() instead of crashing
   Status: RESOLVED. See PR #260 for diff.
