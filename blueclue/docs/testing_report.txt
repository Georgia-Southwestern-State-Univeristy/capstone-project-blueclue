TEST CASE 4 - EDGE CASE
Name:    Simple / Abbreviated Message Classification
Type:    Edge Case
================================================================================

DESCRIPTION:
  Users frequently type terse or informal messages with abbreviations. The
  classifier must handle these without failing to a generic "other" category.
  Tests the abbreviation expansion preprocessor added after initial accuracy
  issues.

INPUTS TESTED:
  A. "pc wont turn on"
  B. "forgot my pw"
  C. "wifi not working"
  D. "printer broke"
  E. "cant log in"

EXPECTED RESULTS:
  A. category = "hardware",  subcategory = "power"
  B. category = "login",     subcategory = "password"
  C. category = "network",   subcategory = "wireless"
  D. category = "hardware",  subcategory = "printer"
  E. category = "login",     subcategory = "authentication"

ACTUAL RESULTS:
  A. hardware / power     (confidence: 0.72)    PASS
  B. login / password     (confidence: 0.81)    PASS
  C. network / wireless   (confidence: 0.85)    PASS
  D. hardware / printer   (confidence: 0.78)    PASS
  E. login / authentication (confidence: 0.84)  PASS

OUTCOME: PASS (5/5)
NOTES:   Before the abbreviation expansion fix, "pc wont turn on" returned
         category = "other" because the classifier required "won't" as the
         full contraction. "forgot my pw" returned "other" because "pw" was
         not in the keyword vocabulary. Both now expand correctly before
         classification. Test suite for simple messages grew from 0 passing
         cases to 8/8 after this fix (per CHANGELOG.md).

TEST CASE 5 - EDGE CASE
Name:    Wireless Mouse Category Ambiguity
Type:    Edge Case
================================================================================

DESCRIPTION:
  The message "Mouse keeps disconnecting from wireless receiver" contains
  hardware keywords ("mouse", "receiver") AND network keywords ("wireless",
  "disconnect", "disconnecting"). This tests how the classifier resolves
  a cross-category ambiguity.

INPUT:
  "Mouse keeps disconnecting from wireless receiver"

EXPECTED RESULTS:
  category   = "hardware"  (mouse, receiver are hardware devices)
  subcategory = "peripheral" or "wireless"
  confidence >= 0.60

ACTUAL RESULTS:
  category   = "network"   (confidence: 1.00)
  subcategory = "connectivity"
  keywords matched: ["wireless", "disconnect", "disconnecting",
                     "keeps disconnecting"]

OUTCOME: FAIL
ANALYSIS:
  The keywords "wireless", "disconnect", and "disconnecting" have high weights
  (3.0-4.0) in the network/connectivity category. The hardware keyword
  "mouse" has a lower weight (2.0). The network keywords collectively score
  higher and win. Confidence of 1.00 shows the scorer is very certain about
  the wrong answer.

  This case is documented in test_results.md as a known failure. It represents
  an inherent ambiguity in the keyword overlap between hardware peripherals
  and network connectivity. The fix would require a compound rule: if
  "wireless" + "mouse" co-occur, score hardware/peripheral over
  network/connectivity.

IMPACT:   Low - this is a rare ticket type. The technician can manually
          recategorize after submission with one click.
TRACKED:  Yes - this exact case is documented in the failed tests section
          of test_results.md as a known limitation.

TEST CASE 9 - ERROR HANDLING
Name:    AI Service Unreachable During Ticket Submission
Type:    Error-Handling
================================================================================

DESCRIPTION:
  The backend is configured with AI_SERVICE_TIMEOUT=5000ms and
  AI_MAX_RETRIES=2. When the AI service is down, ticket creation must
  still succeed using the rule-based fallback. The system should not
  return a 500 error to the user because the AI is unavailable.

SETUP:
  AI (ml-service) container stopped: docker compose stop ml-service

INPUT:
  POST /api/tickets with a valid ticket body
  (subject: "Screen is cracked", description: "Laptop screen cracked badly")

EXPECTED RESULTS:
  - HTTP 201 Ticket created successfully (not 500)
  - ai_classified = false in the tickets table
  - ai_fallback_used = true (or equivalent flag)
  - category and priority set by rule-based fallback
    (confidence ~0.3 indicating low certainty)
  - User-facing response does not mention "AI service error"
  - Backend logs show: "AI service unavailable, using fallback classification"

ACTUAL RESULTS:
  - HTTP 201 returned with ticket object                         PASS
  - ai_classified = false                                        PASS
  - category = "hardware" (rule-based: "screen", "cracked")     PASS
  - priority = "medium" (default rule-based priority)
    confidence = 0.30                                            PASS
  - Response message to user: "Ticket submitted successfully"
    (no error message shown)                                     PASS
  - Backend log line: "AI service unavailable, falling back to
    rule-based classification"                                   PASS

OUTCOME: PASS
NOTES:   The backend retried the AI endpoint 2 times (AI_MAX_RETRIES=2) with
         5000ms timeout each before giving up and using fallback. Total added
         latency: ~10.1 seconds from the user's perspective. This is an
         acceptable tradeoff for graceful degradation - the ticket is created
         and the AI can re-classify it when the service is restored.
         Service restored by: docker compose start ml-service

TEST CASE 12 - ERROR HANDLING
Name:    Stale Chat Handoff Claim Auto-Release
Type:    Error-Handling
================================================================================

DESCRIPTION:
  When a technician claims a chat handoff but disconnects without resolving
  it, the conversation becomes permanently locked to that technician.
  No other tech can claim it. The system must automatically detect and
  release stale claims so the customer is not left waiting indefinitely.

SETUP:
  chat_conversations row with:
    handoff_requested = true
    handoff_claimed_by = [technician_id]
    handoff_claimed_at = 2 hours ago
    ended_at = null

INPUT:
  node-cron scheduled job fires (or manual trigger of the stale handoff
  release function)

EXPECTED RESULTS:
  - handoff_claimed_by reset to NULL
  - handoff_claimed_at reset to NULL
  - Conversation becomes available for any technician to claim
  - Technician workload dashboard shows conversation as "waiting" again
  - Socket.IO event broadcast: 'handoff_available' emitted to technician rooms

ACTUAL RESULTS:
  - handoff_claimed_by = NULL after cron job                     PASS
  - handoff_claimed_at = NULL                                    PASS
  - Conversation visible again in technician handoff queue        PASS
  - A second technician was able to claim it immediately          PASS
  - Socket.IO 'handoff_available' event received by clients
    (verified in browser DevTools Network tab)                   PASS

OUTCOME: PASS
NOTES:   This bug was discovered when conversation id=10 became permanently
         stuck in production. Migration 037 (037_reset_stale_handoff_claims.sql)
         was applied directly to the Railway database to fix the immediate
         stuck record. The cron-based auto-release was then implemented as
         the permanent preventive solution. The direct SQL fix is documented
         in the terminal history:

           UPDATE chat_conversations
           SET handoff_claimed_by = NULL,
               handoff_claimed_at = NULL,
               handoff_resolved_at = NULL,
               ended_at = NULL
           WHERE id = 10;
